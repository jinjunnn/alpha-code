## 3. `#1099` 埋点:直接指名到步

**`renderer.projects.connect` → `renderer.projects.store_ready`(第一次拿到项目列表)**

| | |
| --- | --- |
| 36 个稳态样本 | **1,182 – 7,080 ms** |

**整个启动的稳态 P95 是 8,313,这一步占了 7,072。** 它的波动幅度(5.9 秒)比整个启动的波动还大。

| --- | --- | --- | --- |

| 其余十五步(各自) | — | — | 全部在 ±41 ms 内 |

⇒ **下一步的目标已经具体到一个步骤**,不必再猜。

## 4. 为什么有一批数据不用于判过线

第一批三轮跑在 05:13–05:18,**负载 4.84 – 11.05**,`siriknowledged` 占 80–92% CPU、
`swcd` 占 64–80%(macOS 唤醒后的索引/同步守护进程)。那批算出的合并 P95 是 5,019.7 ms ——
**超线仅 20 ms**,远小于该负载可能造成的偏差。

按 `#1095` 立下的口径(每个样本连负载一起记,用它排除 CPU 抢占这个解释),**那批不能用来判过线**。
数据保留为 `*-noisy-*`,因为其中两条结论不受负载影响:看门狗的千倍改善,以及
「`store_ready` 是波动主因」(同一样本内部的相对比较,两边受同样影响)。

重跑的这批负载 1.69 – 6.78(中位 3.60),且余量 3.3 秒,结论稳。

## 5. 打包这一段的坑(下一个人会再踩)

仓内 `packages/ui-mac/electron-builder.config.ts` **显式把 `mac.identity` 设为 null**,
打包日志只有一行 `skipped macOS code signing  reason=identity explicitly is set to null`。
产物因此只带 Electron 自带的 adhoc 签名,而 bundle 内容被 electron-builder 改过、密封不一致 ⇒
`spctl` 报 `code has no resources but signature indicates they must be present`,**应用起不来**。

此时探针的表现是:13 个样本全失败、结果文件里 **0 个样本**、**而 exit code 仍是 0**。
一路上没有任何一环自称失败。

本轮用的本机配方在 `#1095` 那份之上再补一件事:把 `mac.identity` 指回钥匙串里的 Developer ID
(名字**不能带** `Developer ID Application:` 前缀,electron-builder 会拒)。
`#1095` 那份配方解决的是另一个问题:**本网络连不上 Apple 的时间戳服务**,而 Developer ID
签名会隐式索要时间戳 ⇒ 必须关时间戳、关公证、只出 `.app`。

两份配方都是**本机一次性**的,不入仓。
