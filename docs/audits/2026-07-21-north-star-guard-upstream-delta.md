# North-star guard 上游 delta — 逐文件裁决

> 只读调查。裁决权归 owner;本文只判定与建议,不设计重构。
> 追踪 Issue = [alpha-code#456](https://github.com/jinjunnn/alpha-code/issues/456)。

## 地面真相:21 个文件 = 一个提交 = 一个决定

守卫口径(`alpha-ci.yml` north-star guard,`git diff --diff-filter=DMR --name-only
origin/dev...origin/alpha -- $UPSTREAM_PATHS`,`UPSTREAM_PATHS = packages/{opencode,core,server,tui,sdk}`)
下 alpha 相对 dev 改了 21 个上游文件。**这 21 个文件的 alpha 侧 delta 全部由同一个提交引入**:

- `fd357d58` `feat(protocol): permission decisions gain immutable fingerprints and durable receipts (#433) (#437)`
- 作者 `jinjunnn`(+ Claude Fable 5),2026-07-20;alpha-only(不在 `origin/dev`)。
- 6-commit squash(1 实现 + 4 轮 review 加固 + 1 契约文档);实现 **REQ-090 AC3/AC8「补齐 Permission DTO 与幂等 reply 语义」**([#433](https://github.com/jinjunnn/alpha-code/issues/433) CLOSED,PR [#437](https://github.com/jinjunnn/alpha-code/pull/437) MERGED)。
- 提交共动 36 个文件;只有 21 个落在守卫的 5 个包根内。其余落在 **未被守卫**的 `packages/{protocol,schema,client,httpapi-codegen}` 与 `docs/`(见文末「守卫盲区」)。

其它 `git log` 里出现的 `3b638e4a` / `fcf404d7` / `e8e883d4` / `6c89687a` / `4245f3bf` 都是 **dev→alpha 的 merge/sync 提交**,不是 alpha 自有的实质改动。

**因此「21 个文件的 A/B」本质上是一个决定**:REQ-090 是否有权让 alpha 直接接管上游 permission 引擎/契约表面。这是一次**真实的主权收编(产品所有权专项:alpha 拥有确认/授权表面),不是意外漏改**——但它被以 **L4(直接编辑仍在同步的上游文件)** 的形态执行,而 ADR-029 明文规定 **L4 永不设立**。所以正确处置既不是天真的「只更新守卫范围」,也不是天真的「全部退回 seam」,而是:

- 构成**被接管的 permission 表面**的文件 → 走 **L3 冻结接管**(ADR-020 先例),经**一条新 ADR** 把它们从守卫范围移出并声明放弃该范围上游白嫖;
- 只是**本可避免的连带改动**(为迁就 alpha 更严校验而顺手改的上游文件)→ 判 **B**,重构 alpha 侧设计让它们退回上游原样。

## 权威口径回顾(判定依据的宪法锚点)

- **ARCHITECTURE 硬约束#1**:`packages/{opencode,core,server,tui,sdk}` 上游文件**只读、永不修改**;守卫 = 上述 diff 非空即红。ADR-020 已把 `packages/{app,ui}` 移出(冻结本意)。
- **ADR-004**:升级隔离;修改类 allowlist 仅 `bun.lock`;`/api/*` 走 `patches/`(loud-fail)。
- **ADR-029 上游主权阶梯**:铁律不修宪,主权升级走四级枚举通道——**L0 接缝**(plugin/tool/MCP/sidecar/config,只增不改)、**L1 变换**(build/runtime transform,磁盘不动)、**L2 补丁**(`patches/`,loud-fail)、**L3 冻结接管**(文件退出同步集,alpha 全所有权,放弃上游白嫖,唯一写=受控 re-freeze)。**不存在 L4(直接编辑同步中的文件)**。升级须逐案 ADR,先给「低级别不可行」的勘探证据。
- **ADR-020**:L3 的既有实现范式——`alpha-ci.yml` 的 `UPSTREAM_PATHS` 移除被接管路径 + 写 ADR + 声明放弃白嫖。
- 关键 seam 事实:opencode **存在** permission 接缝 `plugin/src/index.ts:261` 的 `permission.ask` hook,但它只产出 `"ask"|"deny"|"allow"` 决策,**无法**改 wire 协议(fingerprint/receipt/409)、reply 形状(204→receipt)、或加 DB 持久化。REQ-090 要的正是后者,故 L0 接缝**不够用**——这是判「非真漏」的核心证据。

## 小结①:建议移出 UPSTREAM_PATHS 的集合(A 类)+ ADR 处置

REQ-090 permission adjudication 是**真实主权收编**,应走 **L3 冻结接管**,但**需要一条新 ADR**(不能只改 `alpha-ci.yml`)。建议:

1. **新 ADR(暂名 ADR-033「Permission 内核接管」)**,引用 ADR-029 §3 流程,把下述**被接管表面**挪到 L3:
   - `packages/core/src/permission.ts`、`packages/core/src/permission/**`(引擎 + 持久化表定义)
   - `packages/server/src/handlers/permission.ts`(HTTP 契约 handler)
   - `packages/opencode/src/server/routes/instance/httpapi/public.ts` 内的 permission 契约 shim
   - 上述文件对应的上游测试(`core/test/{permission,event,database-migration}.test.ts`、`opencode/test/server/httpapi-exercise/**`、`httpapi-public-openapi.test.ts`)随源。
   ADR 须载明 ADR-029 §3 五要件:触发需求(REQ-090 AC3/AC8)、为何 L0–L2 不够用(seam 只出 allow/deny;协议/receipt/DB 无法 transform/patch 轻量表达)、守卫形态(见 2)、回退方案、**放弃白嫖范围声明**(permission 引擎的上游改进/安全修复不再自动进入)。
2. **守卫改造(比 ADR-020 更细)**:ADR-020 是**整包**移出(`app`/`ui`);本例被接管的是**散落在 core/server/opencode 三个高 churn 包内的少数文件**,不能整包移出。需把守卫从「包根路径」升级为「**路径 - 例外文件**」的显式 allowlist(pathspec 排除:`:(exclude)packages/core/src/permission*` 等),否则会连带放行整包。这是本处置相对 ADR-020 的**新机制成本**,需在 ADR 里定形态。
3. **生成文件整类移出(独立于 A/B)**:5 个 gen 文件(`core/schema.json`、`core/src/database/*.gen.ts`、`sdk/js/src/v2/gen/*.gen.ts`)是**机械产物,从不手写**;对它们做 diff 守卫,只要任一 alpha 拥有的源(迁移/协议/schema)合法变化就误报「上游编辑」。建议把 **gen/快照类文件作为一类移出 `UPSTREAM_PATHS`**,其完整性改由「CI 内重生结果为空 diff」守卫,而非静态 diff。这可**独立于 REQ-090 决定**先落地(消除本类误报源)。可扩 ADR-004 或并入新 ADR。

## 小结②:真漏清单(B 类,4 条)+ seam 退回方向

这 4 条**不属于「拥有 permission 表面」的必需**,是 alpha 侧设计选择的**可避免连带**,应重构使其退回上游原样(退出守卫红,且不进 L3 冻结集——它们都是高 churn 通用文件,冻结代价高):

1. **`core/src/tool/glob.ts`** → 让 alpha 的 wire 校验器把 `undefined` 字段**规范化为缺省**(而非拒绝),caller 无须省略 → 文件退回 upstream。
2. **`core/src/tool/grep.ts`** → 同 glob(同一校验器设计),一并退回。
3. **`core/src/event.ts`** → 把事件冻结从**通用 notify 路径**移到 **permission 事件的发射点**(alpha 被接管代码内)→ 共享事件总线退回 upstream。
4. **`packages/sdk/js/script/build.ts`** → 把 codegen 后的 permission 类型补丁移到 **alpha 自有后置生成步**(而非编辑上游 SDK build 脚本);或若 owner 认可「同文件已有上游 history 补丁、此为自然归宿」,则显式登记为 **L2 patch 面**(ADR-029 L2,须 loud-fail 纪律)。**此条最不确定**,见下。

> 注:B 类退回后,其对应上游测试(如 `event.test.ts` 中针对 `event.ts` 冻结的用例)也随之退回/迁到 alpha 自有测试。

## 最需要 owner 拍板的点

1. **是否接受 L3 接管 permission 内核**(小结①)。这是 21 个文件背后的**唯一实质决定**。它比 ADR-020 的前端冻结更重:(a)被接管文件散落在 core/server/opencode 三个仍高频同步的包内,需要**文件级(而非包级)守卫例外机制**;(b)**永久放弃** permission 引擎的上游 churn 与安全修复(单向门)。ADR-020/ADR-029 先例支持这么做,但维护成本真实。若 owner 不接受 L3,则 REQ-090 需降级重表达(seam/transform/patch),意味回退这次 core 重写——代价同样高。
2. **`sdk/js/script/build.ts` 的归属**(B#4):它是 L1 变换却编辑了上游 build 脚本;同文件已有上游自带的 history 补丁块,使「编辑此文件」看似自然。退回 alpha 自有后置步(判 B)还是登记为 L2 patch 面(判 A-adjacent),二者皆可自洽,需 owner 定调。

## 守卫盲区(附带发现,供 owner 参考,非本次裁决对象)

同一提交 fd357d58 还改了 `packages/{protocol,schema,client,httpapi-codegen}` 内的上游源(如 `schema/src/permission.ts` +87、`protocol/src/groups/permission.ts` +25),但这些包**不在 `UPSTREAM_PATHS`**,守卫**看不到**。若它们同属上游同步面,则守卫范围本身存在缺口(permission wire 契约的真正 SOT 有一半在守卫之外);这解释了为何 SDK gen 的「源」部分落在守卫盲区。建议 owner 一并复核 `UPSTREAM_PATHS` 是否应覆盖这些包。
