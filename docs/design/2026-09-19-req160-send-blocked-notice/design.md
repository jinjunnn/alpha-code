## 1. 与上一稿的关系

**继承**(composer 活稿与现行实现,全部不动):输入框外壳(圆角、细边、聚焦抬升)、
文字区与工具栏的上下关系、工具栏 chips 与发送键的左右分布;以及**输入框内部那条已经存在的
提示槽** —— 今天它住着三条,都在文字区之下、工具栏之上。

**新增**:那条槽里的**第四个成员** —— 用户按下发送、而这句话在本机就被拦下时的提示。
它与既有三条的差别只有两处:颜色换成琥珀(理由见 §3),不带按钮。

**取代**:无。它不替换任何既有提示,也不替换右上角的浮层提示(那条继续服务「发送失败,
请重试」)。

**为什么是这个形态**:这条提示要求用户做的事是**回到自己刚写的那句话上改一改**,而不是
「再点一次」。一个几秒后自动消失的浮层提示在用户开始改的时候已经不在了;把它放进输入框、
贴着那段还没发出去的文字,它才在用户需要它的整段时间里都在。这个仓自己早有同一条推理:
`alpha-composer.tsx:1723-1724` 留着一句「按钮已 disabled,toast 点不出来,**不说等于静默
失败**」,那正是这条槽当初被建出来的理由。

## 3. 契约(批准后即 AC 字面量锚点)

| 项 | 规则 |
| --- | --- |
| 位置 | 输入框内部,文字区之下、工具栏之上,与既有三条同槽。首页与对话页是同一个组件,因此是同一条提示 |
| 形态 | 左侧 3px 琥珀细边 + `--a-warning-subtle` 底 + 两句文字。无图标、无按钮、无关闭叉 |
| 颜色 | 琥珀而非红。红在这条槽里已有确定含义(系统这会儿不行、请重试);这一条不是系统坏了,是这句话要改一下 |
| 出现 | 按下发送且本机词表命中的那一刻。不发给引擎;输入框文字与附件原样留着 |
| 不出现 | 词表没同步下来、或读不到时,**不拦也不提示** —— 没做过的检查不摆出一个做过的样子(同 `current/session-workspace` 沙箱告知的「没有围栏就不说有」) |
| 消失 | 输入框内容一改即消失;发送成功即消失。不计时、不自动淡出、无关闭按钮 |
| 再次发送 | 发送键保持可用。原样再发仍被拦,提示不堆叠、不变化 |
| 不说什么 | 不出现「违规」「禁止」这类给人定性的词;不说命中的是哪个词、哪一类 |
| 键盘 | 不新增可聚焦元素,Tab 次序不变;被拦下后焦点回到文字区,直接可以改 |
| 读屏 | 提示条 `role="alert"`,出现即播报两句全文;图标不存在,因此无 `aria-hidden` 需求。颜色不承载信息 |
| 窄宽 | 横向放不下时次句换行到第二行,两句都不截断、不进悬停 |
| 自动化 | 定时任务命中时**不产生任何界面元素**。按既有失败形态记进那次运行的 `status.json`,摘要用同一句人话 |
| 判据钩子 | `data-alpha-composer-blocked`;反向用例 = 未命中时该元素不存在 |

## 4. 文案

| 槽位 | zh | en |
| --- | --- | --- |
| 事实句 | 这条消息没有发出去 | This message wasn’t sent |
| 说明与出路 | 没有通过内容安全审核。修改后可以重新发送。 | It didn’t pass content safety review. Edit it and send again. |

逐句的理由:

- **「这条消息没有发出去」** —— 先说用户此刻最需要确认的那件事。用户按了发送、界面没有动静,
  第一反应是「卡住了吗?我的字还在吗?」。这一句把状态钉死,而输入框里的文字仍在眼前,两者
  互相印证。沿用既有的「现在发不出去」句式(`alpha.composer.modelNotLoaded`),不另起腔调。
- **「没有通过内容安全审核。」** —— 说明原因,用产品里已经在用的那个说法(时间线空回合行的
  `alpha.timeline.emptyTurnWhy` 就是「未通过内容安全审核」)。**不写「违规」「不当内容」
  「禁止发送」**:那些词把一次匹配说成一次定性,而绝大多数命中是无心撞上的普通词。
  **也不写是哪个词、哪一类**:那是审核侧的信息,说出来等于把词表一格一格地喂给想绕过的人。
- **「修改后可以重新发送。」** —— 给出路,并且是用户真的能做到的那一件事。不说「请重试」
  (原样重试必然再次被拦),不说「如有疑问请联系」(没有这个通道)。
- 与时间线空回合行的分工:那一条是**事后推断**,所以它说「**可能**未通过内容安全审核,也可能
  是模型或网络异常」;这一条是**发送前确知**(本机词表当场命中),所以它可以直说。两句话的
  确定度不同是有意的,不是不一致。

## 5. 帧外说明

- **诚实边界。** 这道拦截跑在用户自己的电脑上,懂技术的人可以绕过它 —— 它**不是安全边界**。
  真正算数的复核与留证在服务端:对话上传时按启用词表复判并写留证记录(方案基线 §2.8 与
  §③「客户端被篡改绕过拦截」一行)。桌面端这一层的价值只有一个:让无心撞上的人**当场**就知道、
  当场就能改,而不是事后在别处才被处理。**这段话属于设计说明,不进界面** —— 界面上写
  「你可以绕过」既无用又难看,写「我们会上传并记录」则是隐私政策与登录页已经承担的告知义务,
  不在这条提示里重复。
- **为什么不加图标。** 本轮实测了琥珀图标在这条底色上的对比度:浅色主题下提示条底色实算为
  `rgb(250,239,225)`,`--a-warning`(`#d97706`)落在其上只有 **2.81:1**,低于非文本图形的
  3:1 下限;深色主题下是 8.39:1。与其为一个主题做例外,不如不要这个配件 —— 两句话已经把事情
  说完,图标不承载额外信息。正文颜色同轮实算:`--a-text` 15.61:1(深色 13.42:1)、
  `--a-text-secondary` 6.81:1(深色 5.46:1),都在 AA 之上;`--a-text-tertiary` 只有 3.61:1,
  因此次句用 secondary 而不是 tertiary。
- **既有三条红提示的对比度是 4.01:1**(`--a-error` 落在 `--a-error-subtle` 上),本稿不动它们 ——
  那是存量条件,不是本次引入的,顺手改会把三条已上线的提示一起改样。
- **没有「为什么被拦」的展开入口。** 展开只能说两种话:重复这两句,或者泄露命中项。两种都不该做。
- **自动化命中时不弹任何东西**,是因为那一刻没有人在屏幕前;它落进那次运行的记录里,与超时、
  引擎报错走同一条既有路径。这是可回滚的默认值,不是需要新建的机制。

## 7. 请 owner 确认的三点

1. **这两句话就这么说,行不行。** 关键取舍是让「内容安全审核」这六个字出现在用户眼前:
   出现 ⇒ 用户知道产品确有这一环(与备案叙事一致,也与时间线那条提示用同一个说法);
   不出现 ⇒ 只能说得更含糊(如「这条消息没有发出去,修改后可以重新发送」),用户会猜是
   网络问题并原样重试。本稿选前者。
2. **用琥珀,不用红。** 代价是它与同一条槽里已有的三条红提示不再一眼同族;收益是
   「你写的这句要改一下」与「系统这会儿不行」两件事在视觉上分得开。反过来做(统一成红)
   也说得通,改回只是一行样式。
3. **定时自动化任务命中时不通知你,只记进那次运行的记录。** 默认如此;若你希望它像其他
   失败一样提醒,那是另一条通知线,需要单独说清楚在哪儿提醒。
