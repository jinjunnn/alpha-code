# 设计:前端与上游解耦策略 —— 让 alpha UI 免疫上游前端 churn

> 2026-07-03 · 决策载体 [[REQ-013]] · 证据 [audits/2026-07-03-frontend-reskin-regression.md](../audits/2026-07-03-frontend-reskin-regression.md)
> 用户诉求(2026-07-03):**「不可能它改一次,我就要跟着改一次。」** 目标 = 上游前端 churn **波及不到** alpha UI,而非"断了有警报"。

## 问题的根(为什么会"跟着改")

alpha 前端**深度复用上游渲染树**:挂 `AppInterface`(整棵 provider/router)、直接复用上游 `MessageTimeline` 等重组件,再用 CSS 挂上游内部 `data-component` 锚点换肤。**换肤依赖的 DOM 是上游组件吐出来的** → 上游一改结构,192 锚点里 94 个当场失效(见审计)。

**根本原理**:凡是 alpha UI 依赖**上游 DOM 结构**的地方,就必须跟上游改;凡是只依赖 **SDK 数据契约**(HTTP/SSE,codegen 稳定、改动少而高声)的地方,就免疫。**解耦程度 = 用 SDK 契约替代 DOM 耦合的程度。** 所有方案是这条原则的不同力度。

## 方案菜单(按"免疫程度"从低到高)

| 方案 | 做法 | 上游改一次,你要改吗? | 工作量 | 保留复用 |
|---|---|---|---|---|
| **A 防护网**(=REQ-012) | 锚点契约测试 + tripwire + 冒烟 gate | **要**(但从静默→红灯提醒) | 小 | 全复用 |
| **B 单锚点适配层**(=C14++) | 一个 alpha 拥有的 inject 层,把上游当前 DOM 重新打上稳定 `data-alpha-*` 锚点;CSS 只认 alpha 锚点 | **要,但只改 1 个映射文件**(非 94 处散落) | 中 | 全复用 |
| **C 高 churn 区自建**(时间线消息/工具卡→真组件) | 重灾区改为 alpha 自有 SolidJS 组件 + **SDK 取数**,不碰上游 DOM;终端/diff/markdown 等重引擎仍复用 | **重灾区不用改**;其余仍要 | 大 | 重引擎复用 |
| **D 全自有渲染层**(ADR-016 终局 / 旧 Strategy C) | 整个会话/时间线/弹窗全 alpha 自有组件,**只吃 `@opencode-ai/sdk`**;上游仅作**无头引擎**(terminal ghostty / diff / markdown)包在稳定 wrapper 里 | **基本不用改**(除引擎内部,那有自己的稳定接口) | 很大 | 仅无头引擎 |
| **E 冻结上游前端**(不合并 `packages/{app,ui}`) | sync 时**排除/钉住**上游前端包,只同步 `core/server/sdk` 引擎层 —— ADR-016 本就**放弃**了白嫖上游前端升级,那为何还继续把它的 churn 合进来? | **不用改**(上游前端根本不进 alpha) | 小 **IF 可行** | 冻结点复用 |

## 关键取舍与诚实风险

- **A 不满足诉求**(用户已否):仍"跟着改",只是有警报。**留作任何方案的安全网**,不作为答案。
- **B** 把爆炸半径从 94 处收敛到 1 处,是**最便宜的止痛**,但没根治"要跟改"。适合作 C/D 的过渡垫脚(C14 本就要做)。
- **C / D 是真免疫**:因为只依赖 SDK 数据契约(稳定、versioned、codegen diff 高声可见)。**代价**:重建工作量;且**重引擎(终端/diff/流式 markdown)不能自建**(NON_GOALS#2 白嫖 core),必须复用——所以"100% 免疫"不存在,D 是**除无头引擎外全免疫**。C 是先啃最疼的时间线、增量走向 D。
- **E 是唯一"上游前端根本碰不到你"的路,也最便宜——但可行性存疑**:ui-mac 经 `workspace:*` 从源码构建 `@opencode-ai/app`+`@opencode-ai/ui`,它们与 `sdk/core` 同仓联编。**只钉前端、继续升引擎 → 版本偏斜**(前端期望的 sdk/core 与新引擎不匹配)可能编译/运行崩。**需一个 spike 实测**:能否把 `packages/{app,ui}` 排除出每日 merge 而不引入偏斜;若能,这是性价比之王;若不能,退回 B/C/D。

## 推荐(供决策)

**分层组合,而非单选:**
1. **立刻**:上 **A 防护网**(REQ-012)——不管走哪条,先让下次 sync 的断裂变红灯,止血。
2. **过渡**:上 **B 单适配层**(并入 C14)——把 94 处散耦合收敛成 1 处,后续无论 C/D 都受益。
3. **spike**:并行验 **E 可行性**——若上游前端能安全冻结/排除出 sync,直接拿"永不波及",省下 C/D 大部分重建。**这是最该先验的一张牌**(便宜且可能一劳永逸)。
4. **根治(E 不可行时)**:按 **C→D** 增量重建,从时间线工具卡(94 死锚点主集中地)起步,逐步把 UI 依赖从"上游 DOM"迁到"SDK 契约"。

**一句话原则**(建议写进 ADR-016 修订):**alpha UI 只允许依赖 `@opencode-ai/sdk` 数据契约,不得依赖上游 DOM 结构;凡复用上游组件必经 alpha 拥有的稳定 wrapper/适配层,禁止 CSS 直挂上游内部锚点。**
