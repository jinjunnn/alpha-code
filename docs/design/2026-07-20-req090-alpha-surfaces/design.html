A · 挂载真相

#204 的 route manifest 是否同时拥有非 URL surface composition？

Settings / Model / Dialog 是 overlay，Permission 是 route-inline，Recovery 在窗口创建前。只表达 URL 无法成为 AC6 的唯一真相。

A
推荐：manifest 增加 mount kind + 唯一 owner

URL codec 仍只服务 route；同一份 manifest 额外声明 overlay / inline / boot 的宿主与唯一 owner。最小、可静态校验，也不会把 Recovery 伪装成页面。

B
URL manifest + 单独 overlay registry

改动看似小，但会形成两套 composition 真相，无法用一个 XOR 守卫证明唯一挂载。

C
把五类都建成 URL route

Permission 和 boot Recovery 的生命周期不匹配，回退/刷新语义会被迫造假。

type SurfaceEntry = {
  id: "settings" | "model" | "dialog" | "permission" | "recovery"
  owner: "alpha.settings" | "alpha.model" | "alpha.dialog" | "alpha.permission" | "alpha.recovery"
  mount:
    | { kind: "overlay"; host: "alpha-overlay-root" }
    | { kind: "inline"; route: "session"; slot: "before-composer" }
    | { kind: "boot"; host: "alpha-boot-window"; phase: "pre-window" }
}

settings/model/dialog → overlay
permission            → inline(session, before-composer)
recovery              → boot(pre-window)
B · Permission 契约

公开 request 补齐字段，并把重复提交从错误变成可证明的幂等语义？

当前公开 DTO 丢失 agent，且没有 scope / expiry；现有重复 request/reply、reject 连带与 always 批量行为无法满足 AC3 / AC8。

A
推荐：不可变 request fingerprint + 持久 decision receipt

公开主体、action、资源、作用域、有效期；create/reply 都按 requestID + fingerprint 识别 exact retry。reply 完成后保留收据，不立即删除全部幂等事实。

B
只给 UI 补展示字段，维持现有 reply 语义

能画出五项事实，却无法证明重复点击、崩溃重试和持久授权的原子结果。

C
由 renderer 推断主体 / scope / expiry

会让展示层成为授权真值，存在 confused-deputy 与静默扩大范围风险。

PermissionRequest {
  id, sessionID, fingerprint,
  subject: { kind: "agent", id },
  action,
  resources: ResourceConstraint[],
  scope: { kind: "session", sessionID } | { kind: "project", projectID },
  expiresAt: timestamp | null
}

PermissionReply {
  requestID, requestFingerprint, decisionID,
  decision: "reject" | "once" | "always",
  grantScope?, grantExpiresAt?
}

PermissionDecisionReceipt {
  requestID, requestFingerprint, decisionID, decision,
  committedAt, resolvedRequestIDs
}
情况定义结果
create exact retry同 request ID + 同规范化 payload / fingerprint返回同一 pending request；若已完成则返回同一 receipt
create conflicting retry同 request ID + 不同 fingerprintConflict；不覆盖、不合并
reply exact retry同 request/fingerprint + 同 decisionID + 同决策、scope、expiry返回同一 receipt；不重复授权、不重复执行
reply conflicting retry同 request 或 decisionID，但决策、scope、expiry 任一不同Conflict；保留首个已提交事实
reject只拒绝目标 request不得连带拒绝同 Session 其他 pending
always原子写 grant + 解决目标 request其他 pending 独立按新 policy 重评，并各自产生 receipt；不隐式共用回复
C · 崩溃回退

五类新 surface 是否彻底取消 legacy reload fallback？

现有 SurfaceBoundary 的“reload 后回旧版”与 AC6 的唯一挂载互斥；保留它就等于在生产里继续保留第二套 UI。

A
推荐：五类 alpha-only，无 legacy 回退

失败处置改为同一 Alpha host 内重建当前区域、返回调用面、重启应用或进入 boot Recovery。Permission 始终 fail closed；Settings/Model 保留未提交输入；不跨到旧组件。

B
只在崩溃时回旧界面

用户最脆弱时进入不同交互与权限语义，也让旧 observer / CSS / Portal 无法删除。

C
按 surface 自由决定

会把 fallback 重新变成五份局部政策，无法由 manifest 和测试统一证明。

替代失败处置：overlay 崩溃 → 关闭并保留调用面/未提交值，可重新打开；Permission 崩溃 → 工具继续阻塞，显示最小“重试或拒绝”行；区域崩溃 → 只重建该 Alpha 区域；启动失败 → 独立 boot host 提供恢复/重试/退出。所有路径都使用稳定错误码与本地脱敏日志，不渲染 legacy surface。
D · 模型目录真源

是否、何时把完整模型目录改为运行期从 platform 拉取？

用户预期代理节点来自 platform / web 的运行期完整目录；现状不是。alpha-models.json 是随包发布的本地配置真源，保存名称、tier、variants 与 BYOK 预设；platformProvider 只是网关 provider 壳。运行期 /v1/models 只返回 edition allowlist，用于收窄本地快照，并不提供完整展示目录。

A
推荐：本票不改目录来源，另开需求裁决运行期目录

REQ-090 只完成 picker typed contract 与旧 DOM 链路删除；UI 合同预留运行期“不可用 / 余额不足 / 需登录 / 需 KEY”等事实位。由 owner 另行决定 full catalog API、缓存、版本、降级与 rollout。

B
本票同时改成 platform 完整目录

会把 API 形状、缓存一致性、离线降级、未知模型元数据与发布兼容一并扩入，超出 REQ-090 的界面机制范围。

C
永久维持本地完整目录

发布简单，但平台上下线模型时，客户端可能因同步失败、陈旧缓存或缺少新模型元数据而不知情或只显示退化 ID；目录漂移成为长期产品风险。

范围边界：D 不属于 REQ-090。当前实现可在成功取得 allowlist 时收窄网关模型；它仍不能替代完整目录真源。Owner 若选择运行期目录，应另开需求并定义权威 API、缓存时效、离线快照、未知 ID 处理和下线语义。
