## 背景/证据
云能力有两条数据出境通道(ADR-021):**显式** = 云 dispatch(diff/objective 出境)、**隐式** = platform 代付(每条 prompt 含读入上下文的文件内容持续出境)。ADR-021 §4 预留两个 consent 挂钩点但把时机留给 B16。重启条件(GOALS 判定「临近」)已齐:非技术用户入画像(REQ-008 D3)+ 云派发已实际可用(B3/REQ-020 verified)。用户 2026-07-06 拍板 **GO**。

## 决策(ADR-021 §3/§4 定位:显式=可执行同意门,隐式=诚实告知不装过滤)
1. **显式通道(A 侧,per 项目首次派发同意门)**:hub 云派发在 main 侧 gate —— 该项目 `.alpha/prefs.json` 无 `cloudConsent` 时弹原生对话框(诚实列出境内容/去向/可拒绝/per-项目记录 + 「我已知悉」勾选)→ 同意即写 prefs、放行;拒绝返回 `consent-declined` 不派发。同意版本化(告知实质变更 bump 版本触发重弹)。
2. **隐式通道(C 侧,登录告知不阻断)**:授权同意页加平台代付告知行(对话内容经平台处理出境 + BYOK 逃生 + 隐私政策链接);隐私政策修正 §2 误导 + 增专章(平台代付默认 / 云执行可选 / BYOK 逃生 / 首次云派发 per 项目同意)。

## 验收标准
1. 未同意项目首次 hub 云派发 → 弹同意门;拒绝 = 不派发、行内提示;同意 = 派发且 `.alpha/prefs.json` 落 cloudConsent;
2. 已同意项目再次派发 → 不再弹(版本一致);
3. 同意门文案诚实(列出境内容/去向/逃生),写盘失败不静默放行(反 placebo);
4. C 侧授权页有代付告知 + /privacy 有出境专章,措辞与 A 侧口径一致。

## 非目标 / 已知残余
- **不做隐式通道过滤/改写**(ADR-021 §3:破坏编码任务 + 给虚假安全感);义务止于告知 + BYOK 逃生。
- **MCP facade(agent 会话内 cloud.* 工具)派发不经 main → 本 per-项目门不覆盖**:该路径是会话内用户显式指令触发,B 侧 schema 校验兜底;隐式告知已在登录承担。收窄覆盖如需,另立项。
- 云自动化(REQ-025)派发到 B 直连、不经 cloud-dispatch IPC → 同意语义归其创建流,本门不覆盖(仅任务文本上云,无项目文件)。
- **verified 待真机**:同意门实拍 / 拒绝路径 / prefs 落盘 / 二次不弹 → 下一真机批。
